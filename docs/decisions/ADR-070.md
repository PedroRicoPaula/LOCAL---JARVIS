## ADR-070 — pnpm, and finishing a migration that had been left half-done

**Status:** accepted

**Context.** A migration from npm to pnpm was started 2026-08-17 and left
in the worst possible state: both `package-lock.json` files deleted but
the deletion uncommitted, both `pnpm-lock.yaml` files present but
**untracked**, and a `ui/pnpm-workspace.yaml` containing pnpm's own
unanswered prompt text (`unrs-resolver: set this to true or false`).

That state is worse than either package manager. The published repo still
told anyone cloning it to use npm; the machine it was developed on used
pnpm; and the lockfiles that would have made those agree were sitting
untracked, so no second machine could reproduce the install. `make check`
happened to keep passing, which is exactly what let it sit for five days.

The migration was real, not an abandoned experiment -- `node_modules/.pnpm`
exists in both the root and `ui/`, and pnpm 11.22.0 is installed.

**Decision.** Finish it rather than revert it.

- **Both lockfiles committed.** A lockfile that is not in the repo is not
  doing its job.
- **`packageManager: "pnpm@11.22.0"` in both `package.json` files.** With
  Corepack enabled this makes the pin authoritative: running `npm install`
  fails loudly instead of silently writing a second lockfile that
  disagrees with the first.
- **`Makefile` and `README.md` updated.** The Makefile still ran
  `npm run lint && npm run build`, and the README never documented an
  install step at all -- a fresh clone had nothing to follow. `npx` calls
  were left alone: they resolve from `node_modules/.bin` and work
  unchanged under pnpm, verified by a green `make check`.
- **`ui/pnpm-workspace.yaml` answered: `unrs-resolver: false`.** pnpm 11
  blocks dependency install scripts by default as supply-chain hardening
  and asks per package. `unrs-resolver` is a transitive dependency of
  eslint's import resolver; its `postinstall` is the standard napi
  fallback, and the platform binary it would fetch
  (`@unrs/resolver-binding-darwin-arm64`) already installs as an
  optionalDependency -- confirmed present on disk. So the script is not
  needed, and not running arbitrary install scripts is the safer default
  for a project whose whole security model is about not executing things
  unprompted (CLAUDE.md § 5's spirit).

  Verified rather than assumed: with the script blocked, real `pnpm lint`
  and `pnpm build` both pass. If a future platform ever fails to resolve
  the binary, the failure is loud (module not found), not silent -- flip
  it to `true` then, and the file says so.

**Consequences.**
- `git status` is clean for the first time in five days.
- `make check` green: 577 TS + 118 Python.
- A fresh clone now has one documented, reproducible install path.
- **Not changed:** `npx` in the Makefile. It works, and swapping it for
  `pnpm exec` would be churn for no behaviour difference.
