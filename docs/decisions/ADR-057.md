## ADR-057 — Real performance fixes for gesture tracking, found by measuring, not guessing

**Status:** accepted

**Context.** Owner reported real glitches in the camera/hand-tracking
dashboard display, suspecting the system was running near its resource
ceiling. Measured before touching anything, per this project's own
"verify live, don't guess" discipline (the same one that caught the
mirroring bug and the mask-shape bug in ADR-055/056): a real 5-second
run of the full `GestureLoop` (real camera, real MediaPipe hand tracker,
real segmenter) on this 8GB M1, sampling process CPU time via
`resource.getrusage`.

**What the numbers actually said.**
- Hand detection alone: 44% of one core.
- Adding background blur: 79% of one core -- blur nearly *doubled* the
  loop's own cost, a bigger jump than blur's ~17ms/call in isolation
  should explain on its own.
- Adding pointer control on top of that: 78% -- statistically
  indistinguishable from blur alone. Pointer control was never the
  problem; blur was.

**Root cause, found by profiling the blur path specifically**: blur ran
on the *full* 960x640 captured frame -- segmenting, blurring, and
compositing four times the pixels of the 480px-wide preview that frame
was going to be downscaled to anyway, immediately after, by
`encode_preview`'s own resize. Nobody ever saw the extra resolution;
it was pure wasted work on every single preview frame.

**Fixes, in order of what actually moved the number:**
1. **Resize before blur, not after.** `resize_for_preview` extracted out
   of `encode_preview` and injected into `GestureLoop` the same way
   `mirror`/`encode` already are, so blur (when on) now runs on the
   already-downscaled frame.
2. **Background "obscured," not blurred** -- also an owner request
   ("completamente ofuscado," so the background never competes visually
   with the shapes/skeleton overlay drawn on top): swapped the 35px
   Gaussian convolution for a weighted blend toward the dashboard's own
   `--color-jarvis-bg` colour (`cv2.addWeighted`, alpha 0.92). Cheaper
   than a Gaussian blur *and* more completely obscured -- both wins came
   from the same change, not a trade-off.
3. **Preview is skipped entirely while pointer control is active.**
   Owner's own framing: using the real cursor means looking at the real
   screen being pointed at, not the dashboard's camera panel -- so
   encoding and sending a preview nobody's watching is pure waste.
   `hand.landmarks` (what pointer control itself runs on) is unaffected,
   emitted every frame regardless. The dashboard's gesture panel still
   shows the live skeleton overlay (drawn from that same landmark
   stream) even with the camera image itself switched off, and says so
   rather than showing a stale "waiting for camera" message.

**Result, re-measured the same way**: blur's own marginal cost dropped
from +35 percentage points (44% -> 79%) to +10 (43% -> 53%) -- roughly a
3x reduction, on the same machine, same method, same 5-second window.

**Consequences.**
- 103 Python tests (was 100), 492 TS, `make check` green. New tests:
  `resize_for_preview` (downscale + no-op-when-already-small), and a
  regression test confirming zero `hand.preview` events are emitted
  while pointer control is on (landmarks still emitted every frame).
- `GESTURE_BLUR_KERNEL` config removed (dead: nothing calls
  `cv2.GaussianBlur` anymore); `GESTURE_OBSCURE_BGR`/`GESTURE_OBSCURE_ALPHA`
  added.
- **Owner-required**: whether the dashboard glitches the owner actually
  saw are now resolved needs the owner's own real use to confirm --
  this fixes the one real, measured cost concentration found, but
  "some glitches" was a report, not a fully reproduced bug with a
  before/after screen recording.
