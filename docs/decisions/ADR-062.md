## ADR-062 — Three real bugs found by driving the live system end to end

**Status:** accepted

**Context.** Rather than reasoning about the pipeline, the real `core`
was booted against fake `ears`/`voice`/`eyes` sockets (same newline-JSON
protocol `senses/ipc.py` speaks) on an isolated port and a copy of the
real database, then driven through its own dashboard WebSocket exactly
the way the browser test console does. Every HTTP endpoint answered;
all 13 skills loaded. `/api/routing-misses` was then read for real
utterances from the owner's own history that had failed to route, and
those were replayed live. Three genuine bugs fell out, plus a fourth
finding recorded separately below.

---

**1. Social pleasantries were dispatching to real skills.**

Measured against the full live manifest index, *every* social phrase
tested cleared `CANDIDATE_FLOOR` (0.5), and two cleared `DISPATCH_SCORE`
(0.72) with a runner-up margin wide enough to skip disambiguation
entirely:

| utterance | best match | score |
|---|---|---|
| "how are you" | `brief.morning_brief` | **0.8303** (auto-dispatched) |
| "how's it going" | `brief.morning_brief` | **0.8542** (auto-dispatched) |
| "tudo bem?" | `look.describe` | 0.7544 |
| "obrigado" | `look.describe` | 0.7487 |
| "olá" | `look.describe` | 0.6747 |

So asking JARVIS how it was doing returned a full morning briefing, and
saying thank you came within a threshold of the camera. The owner's own
production history contained the matching real miss: "Como é que tu
estás?" dispatched to `about.list_capabilities`, which read back the
entire capability list.

**Fixed** with `core/skills/socialUtterance.ts`: a no-model, anchored
whole-utterance guard checked at the very top of `dispatch()`, before
any model call at all. Not a prompt fix -- `DISAMBIGUATION_SYSTEM`
already has a "none" escape hatch and the model chose a skill anyway,
and ADR-038 records two separate attempts at rewording that shared
prompt, both of which failed to fix a single case and one of which
regressed two unrelated ones. `core/router/laneHeuristic.ts` (ADR-040)
is this project's own accepted answer to exactly that situation.

Matching is anchored `^...$` after normalization, never substring:
"como estás" is social, "como está o tempo lá fora" is a real weather
dispatch, and the tests assert both. Morning greetings are deliberately
excluded -- "bom dia" measured 1.0000 against `skills/brief`'s own
example and is a wanted dispatch. The must-not-match list in the tests
is the important half of that file.

Side benefit, real on this 8GB machine: a matched utterance now skips
lane classification, the embedding call, and any disambiguation call --
the most common throwaway phrases became the cheapest to answer.

One existing test caught a genuine consequence: `fixtures/goodSkill.ts`
used `"hello"` as a manifest example, so the guard correctly made it
unreachable. The fixture was the unrealistic part (no real skill claims
a bare greeting as an intent example -- that is precisely what the guard
exists for), so its examples became task-shaped. No assertion was
weakened; the test still proves `dispatch()` delegates to the real
pipeline.

**2. "open Instagram" dead-ended instead of opening Instagram.**

Replaying the owner's own logged miss, "in a new tab, open Instagram."
routed to `launcher.open_app` (0.6541, beating `open_url`'s 0.5842 --
`open_url`'s examples are bare domains like "go to google.com", so a
brand name never matched it), and `open -a INSTAGRAM` failed with
"Unable to find application named 'INSTAGRAM'".

**Fixed** in `skills/launcher/index.ts`: when an `open_app` proposal
fails *specifically* because no such application is installed, and no
`path` is involved, the skill proposes `open_url` for `<name>.com` and
says plainly what it substituted -- "There's no app called Instagram on
this Mac, so I opened Instagram's website instead." Never a claim that
the app opened.

Guessing `.com` is acceptable *here specifically* because the guess is
already narrowed to a name macOS just confirmed is not an app, and the
result is a visible browser tab the owner can close -- the same
"immediately visible, trivially reversible" property that put
`APP_CONTROL` in the green tier at all (CLAUDE.md § 5). It is not a
general URL-resolution strategy.

**Confirmed before navigating, after this change's own security review
(2026-08-17).** A dedicated `security-auditor` pass rated the automatic
version MEDIUM: `websiteGuessFor`'s slugification is genuinely safe
(NFD-normalized, everything outside `[a-z0-9]` stripped, so no embedded
dot, hyphen or homoglyph can survive to form a different or punycode
domain -- no injection, no open-redirect), but the *business logic* was
the exposure: plenty of real brands do not own the bare `.com` of their
name, so an always-listening mic plus fuzzy LLM extraction could
silently navigate the browser to a parked or squatted domain nobody
verified. An explicit `open_url` request carries the owner's own words
for the destination; this is a guess the system made, and those are
different things. Now the skill reads the guess back and asks first
(`ctx.ask`, ADR-013's own primitive), using a new bilingual
`skills/_shared/affirmative.ts`. That helper is deliberately
three-valued -- yes / no / **unclear** -- and an unreadable answer is
treated as "no", because proceeding on an answer that could not be read
would defeat the point of asking. One extra turn, only on this rare
fallback path.

Deliberately skipped when a `path` is present: that is `open_project`
opening a real editor, where "Cursor isn't installed" must stay an
honest error and must never become a trip to cursor.com. A test asserts
exactly that, and another asserts an unrelated launch failure (-10810)
is still reported honestly rather than silently turned into a website.

The not-installed detection lives in the skill, not the executor,
because a skill cannot import `core/executors/**` (CLAUDE.md § 5b,
ESLint-enforced) -- and because deciding what to *do* about a failed
outcome is the skill's own job, the same way `speechForOutcome` already
interprets one. Verified on this machine rather than assumed: `open`'s
message is **not** localized (a pt-PT system still prints the English
string), unlike `osascript`, whose errors on the same machine are
translated. If that ever changes the check returns false and the old
honest-error behaviour is what remains -- never a wrong action.

**3. Portuguese replies were Brazilian Portuguese, not European.**

One real reply carried five separate Brazilian forms: "gerenciar",
"aplicativos", "câmera", "você me disse", "seu Gmail". CLAUDE.md § 0.1
and ADR-033 both specify European Portuguese. `core/persona.md` said
"PT-PT" and stopped there -- which is not enough, because Brazilian
Portuguese is the overwhelming majority of Portuguese in any model's
training data and is what it defaults to absent concrete instruction.

**Fixed** by making `core/persona.md` concrete: address the owner as
`tu` (never `você`/`o senhor`) with European clitic placement
("disse-te", not "te disse"); a table of the substitutions that actually
come up in this system (aplicação/aplicativo, gerir/gerenciar,
câmara/câmera, ecrã/tela, ficheiro/arquivo, rato/mouse, área de
transferência/clipboard, and others); and the tense habit that marks a
reply fastest -- "estou a fazer", never "estou fazendo". With an
explicit note that this is about Brazilian-vs-European choices and not
about purging English technical terms, which real PT-PT speech keeps
as-is.

**Also fixed, a second half of the same gap:** `skills/about` answered
with a hardcoded English string regardless of the language asked in --
"o que consegues fazer?" returned the full English list. A skill whose
answer goes through a model inherits the persona for free; one that
answers from a hand-written string, deliberately (so it can never invent
a capability), does not. It now carries both templates and picks with
`skills/_shared/language.ts`, a deliberate TypeScript port of
`senses/voice/language.py`'s scoring -- same word lists and diacritic
weighting, different side of the pipeline and different runtime, with
the duplication called out in both directions the same way this project
already justified `ConnectionHolder` across the `senses/*` daemons. A
test asserts the PT template contains the European forms and contains
none of the Brazilian ones, plus a structural guard that both templates
describe the same capability set.

**Also found, recorded not fixed: the Gmail OAuth refresh token is dead.**
`core` boots with `invalid_grant: Token has been expired or revoked`
from Google's own token endpoint. This was previously recorded as
"Gmail not configured"; it is configured, and the stored refresh token
is no longer valid. Re-running `bench/gmail_authorize.ts` is the fix and
it needs the owner's own browser -- genuinely owner-required, now with a
precise cause instead of a guess.

**The honesty gap that came with it is closed (same day).** `about` was
listing "check your Gmail" among its capabilities while the server sat
unregistered -- a capability claim is exactly as serious as a factual
claim (CLAUDE.md § 6), and this is the one skill whose entire job is
answering that question honestly. It now checks `ctx.mcp.hasServer()`
(the read-only discovery slice skills already get, built for exactly
this) and claims Gmail/GitHub only when the server is actually
registered right now, in either language, with the sentence staying
grammatical at zero, one or two servers. Verified live against the real
core with the token still expired: the capability list no longer
mentions Gmail.

**Consequences.**
- 517 TS tests (was 498) + 108 Python, `make check` green.
- New: `core/skills/socialUtterance.ts` (+6 tests),
  `skills/_shared/language.ts` (+4 tests), launcher fallback (+6 tests),
  `about` bilingual (+3 tests).
- All three fixes verified live against the running real `core`, not
  only in unit tests: the two social phrases now fall through to
  conversation with natural PT-PT replies, and the capability list comes
  back in European Portuguese.
