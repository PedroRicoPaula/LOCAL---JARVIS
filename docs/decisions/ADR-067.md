## ADR-067 — Two defects a code review caught in this session's own fixes

**Status:** accepted

**Context.** A dedicated `code-reviewer` pass over ADR-064/065/066's
diff found two real defects introduced *by those fixes*. Recorded
because both are the kind that only appear once a change is in place --
neither existed before the code they're in was written.

---

**1. HIGH — the optimistic-write rollback restored a stale snapshot.**

ADR-066 fixed dashboard writes claiming success they never had. The
rollback it added captured `const before = tasks` from the React closure
and called `setTasks(before)` on failure. That looks right and is
wrong: it restores a whole *stale* array rather than undoing the one
thing that failed.

Concrete failure: delete task B (slow request, still pending), then
delete task A (fast, succeeds). B's request finally fails, and its
rollback restores the snapshot taken before B was removed -- which still
contains A. **A is resurrected in the UI despite being genuinely deleted
server-side.** Nothing self-heals it: there is no `task.*` server event
and the lists are only fetched at load, so it stays wrong until a
reload. The same shape can silently discard a concurrent successful
toggle.

Fixed with targeted functional updates instead of snapshots: `toggleTask`
rolls back by toggling the same id again (toggle is self-inverse), and
the two deletes capture only the removed item and re-insert it only if
it isn't already present. Each rollback now undoes exactly its own
operation and nothing else.

---

**2. MEDIUM — a mid-stream failure spoke a partial answer, then recorded
only an apology.**

ADR-064 made `converse` stream. That makes a mid-stream provider failure
a genuinely new case: `routeChat` deliberately rethrows rather than
failing over once it has already yielded output, so by the time the
error fires the owner may already have *heard* part of a real answer.

Letting it propagate meant `core/main.ts` spoke "Something went wrong
handling that. I've logged the error." on top of that partial answer,
and recorded only the apology. The transcript, the dashboard and
`events` would all show a turn in which JARVIS apparently said nothing
but an error, when in fact it said half an answer out loud -- an audit
gap, not just an awkward reply (CLAUDE.md § 6).

Fixed: `generalConversationReply` catches mid-stream. If nothing was
spoken and nothing is buffered, it rethrows and the existing
honest-failure path is unchanged. If something *was* said, it flushes
the tail, adds "Sorry, I lost the rest of that.", and returns the whole
thing -- so what gets recorded is what was actually said.

A second, self-inflicted bug was caught while writing that: `flush()`
empties the buffer, and the first draft called it twice (once in the
guard, once for the tail), silently dropping the tail. It is now called
once and the result reused. Tests assert the spoken sentences reassemble
to exactly the returned text.

**Consequences.**
- 553 TS tests (was 551) + 108 Python, `make check` green.
- Both findings were in code written earlier *in this same session*.
  Worth stating plainly: the live-testing pass found real bugs, and the
  review pass found real bugs in the fixes. Neither substitutes for the
  other.
- The reviewer also confirmed clean, with reasoning: `SentenceAccumulator.
  push()` provably terminates (each iteration consumes >= 2 characters);
  `AskCancelledError` reaches `core/main.ts`'s catch on every real path
  (every `ctx.ask` call site is a direct `await`, and `dispatch()` has no
  try/catch around `skill.handle()`); the `return` inside that catch
  still runs the enclosing `finally`, so the orb cannot stick on
  "thinking"; and `backfillForNewClient` runs after the handshake, so
  the socket is always OPEN.
