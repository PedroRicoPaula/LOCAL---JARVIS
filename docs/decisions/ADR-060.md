## ADR-060 — Reminders `list`/`complete` hang: re-investigated live, narrowed, partially fixed

**Status:** accepted (partial -- see "Still open" below)

**Context.** ADR-052 flagged `list_tasks`/`complete_task` as hitting a
real, precisely-isolated hang against real Reminders.app, suspected
(but not confirmed) to be a macOS Automation-permission (TCC) dialog a
non-interactive process can't see or click -- same category
`focusMode.ts` already documents for Shortcuts.app. Flagged explicitly
as owner-required: try it for real via `make dev` in an actual
interactive terminal.

**Re-investigated directly, 2026-08-13, before treating it as purely
owner-required.** Real, repeated calls to the actual
`runRemindersAction` (not a raw `osascript` guess) against the owner's
real Reminders.app, no permission dialog ever shown or clicked by this
agent at any point:

- `list` against a list with **zero incomplete items** (the common
  case for this owner's real list, which held only completed items):
  resolves in **~1.1s**.
- `add`: resolves in **~10s**.
- Touching a **freshly created or modified item's properties** --
  `list`'s own `.map()` over the filtered array, `complete`'s
  read-back after mutating -- reliably ran past the old 15s
  `TIMEOUT_MS` and failed with the generic `execFile` timeout error.
  Retried with real patience (a background call, tens of seconds, not
  hundreds): **succeeded**. A completed item's properties, read
  directly by index in a *fresh* script invocation days later,
  resolved in 3-5s -- slow, but nowhere near the 15s+ that hangs.
- **The write itself lands regardless of whether the read-back after
  it does**: a `complete` call that failed on timeout was independently
  confirmed, via a later fresh query, to have actually set
  `completed = true` on the real item.

**This shifts the leading theory.** The pattern -- fast for
already-synced/completed items, slow specifically for freshly
created/modified ones, and the write succeeding even when the
read-back after it times out -- is more consistent with Reminders.app's
CloudKit/iCloud sync blocking a property read on an item that hasn't
finished syncing yet, than with a stuck TCC permission dialog (which
would be expected to affect every call uniformly, not correlate with
how recently the item changed). **Not fully confirmed either** -- this
narrows the diagnosis with real data, it doesn't close the loop.

**Decision.** Bumped `TIMEOUT_MS` from 15s to 30s (`core/executors/
reminders.ts`, now exported so the test asserting it's applied
references the real constant instead of a copied-out number) --
real headroom for the common case, still bounded so a genuinely stuck
call fails honestly rather than blocking a `converse`-lane turn
indefinitely. Deliberately not bumped further (60-90s, closer to what
the slowest real retry took): CLAUDE.md § 7's first-audible-syllable
budget makes a JARVIS response that goes silent for a minute a real
UX cost, worse than an occasional honest "couldn't complete that right
now" on the genuinely slow path.

**Consequences.**
- 10 executor tests, unchanged behaviorally, one updated to reference
  the exported constant instead of a hardcoded `15_000`.
- **Still genuinely owner-required, sharpened not removed:** whether
  30s is enough headroom under real, repeated, everyday interactive
  use -- ask "what are my tasks" for real, more than once, including
  right after adding or completing something (the specific condition
  now known to be slow) -- is the one thing that needs the owner's own
  session to observe. If it still fails sometimes, that's now a much
  better-characterized bug report than ADR-052 could give: "slow after
  a recent add/complete, likely iCloud sync," not "hangs, cause
  unknown."
