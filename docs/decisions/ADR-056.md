## ADR-056 — Hand-driven real cursor, click gated by a physical key

**Status:** accepted

**Context.** Owner's follow-on idea to the gesture camera feature
(ADR-053): the real macOS cursor follows the index finger, and saying
"clicar aqui" fires a real click at the cursor's position. A first,
broader version of this (click fires immediately, anywhere on screen,
no confirmation) was explicitly proposed by the owner and refused: a
click that can land anywhere has no way to distinguish a harmless link
from a "Send"/"Delete"/payment-confirm button or a password field, so
it has to be judged by the worst thing it could hit -- which is
red-tier territory, and CLAUDE.md § 5's red tier is explicit that its
actions are "never reachable by a spoken 'yes' alone." A counter-
proposal was made instead and accepted: cursor movement runs freely
(harmless, visible, trivially undone), but a click only ever fires on a
real, physical keypress at that exact instant -- reusing the red tier's
own established pattern ("a real keystroke fires it") as a structural
property of the executor, not routed through the approval queue (which
would be absurd for something as routine as a mouse click, and would
defeat hands-free pointing entirely).

External validation, not just internal reasoning: research into
`farzaa/clicky` (a similar macOS "cursor near an AI" project) found it
goes further in the conservative direction -- it never fires a real
click at all, only animates the cursor as a visual pointer for the
human to look at. This project's design (real clicks, but only on a
real keypress) sits between "no clicks ever" and the refused "clicks
anywhere, no confirmation" -- deliberately.

**Decisions.**

- **`POINTER_CONTROL` is a new green-tier capability**, not routed
  through the yellow approval queue, specifically because the click
  safety is structural (the physical key), not something the Gate needs
  to mediate per-click.
- **Feasibility checked before building, not assumed**: `pynput` (an
  existing dependency, already used for `senses/ears`'s push-to-talk
  hotkey) really moves the macOS cursor -- confirmed with a real
  set/read-back cycle. `Quartz` (already installed as `pynput`'s own
  macOS backend, no new dependency) really reads real screen size
  (1440x900 confirmed on this machine). A real end-to-end run --
  MediaPipe detecting a real test image's hand, mapping the real
  fingertip position through real screen coordinates, moving the real
  cursor there -- was verified live, cursor restored after. No click
  was ever fired during this verification; see "owner-required" below
  for why.
- **Cursor control is layered into the existing `GestureLoop`**, not a
  separate mode -- it already runs hand detection every frame, so
  reusing that avoids running MediaPipe twice in parallel. A dedicated
  `senses/eyes/pointer.py` module holds `PointerBackend` (movement) and
  `ClickTrigger` (the physical key) as separate, independently-testable
  Protocols.
- **Voice-armed, not a dashboard button** -- unlike the blur/theremin
  toggles (cosmetic, contained entirely inside the dashboard's own
  canvas), pointer control reaches the real OS, so arming it carries the
  same weight as arming hand tracking itself: the owner has to say it.
  `start_pointer_control` starts gesture tracking first if it isn't
  already running (idempotent), so pointer control can never silently
  no-op because tracking wasn't on.
- **Click is edge-triggered**, firing exactly once per physical
  key-down, not once per frame while held -- tested explicitly (a key
  held across 4 frames fires exactly 1 click).
- **A real crash, found and fixed during testing, not shipped**: an
  early version of the tests let `set_pointer_control(True)` fall
  through to the real default `click_trigger_factory` (`PynputClickTrigger`),
  which starts an actual macOS-wide keyboard listener thread. Several
  piling up across a test run segfaulted the Python interpreter --
  exactly the failure mode CLAUDE.md § 3's "every module gets a fake"
  rule exists to prevent. Fixed at the root: the test helper now
  defaults `pointer_backend_factory`/`click_trigger_factory` to fakes
  itself, rather than trusting every call site to remember.

**Consequences.**
- 100 Python tests (was 82), 492 TS tests, `make check` green.
- **Owner-required, explicitly not self-tested**: firing a real
  `.click()` during automated verification risks hitting anything on
  the real screen unpredictably -- unlike cursor movement (harmless,
  reversible), a click is a genuine side effect this agent has no way
  to guarantee is safe to fire blind. Cursor movement was verified for
  real; click-firing itself needs the owner's own hand, own key, own
  chosen target.
- Also needs Accessibility permission for the `eyes` process (same
  `pynput` requirement `senses/ears`'s hotkey listener already has) --
  not yet confirmed granted for `eyes` specifically; likely a first-run
  permission prompt, per README's existing Phase 1 note for `ears`.
