## ADR-055 — Hand-tracking fixes from live testing: mirroring bug, background blur

**Status:** accepted

**Context.** Owner tested the hand-tracking camera mode for real (first
real end-to-end use since ADR-053) and reported two things: the hand
skeleton overlay appeared on the wrong side of the real hand ("levanto a
mão e os pontos... estão do outro lado"), and asked for background blur
if easy to add.

**The mirroring bug, root-caused, not guessed.** `GestureLoop.run()`
mirrored the raw frame first, then ran hand detection *on the already-
mirrored frame*, then called `mirror_hands()` on the result. Two flips:
the frame got mirrored once (for the preview), the landmarks got
mirrored twice (once implicitly, by detecting on a pre-flipped frame,
once explicitly by `mirror_hands`) -- net zero, so the landmarks ended
up in *unmirrored* space drawn over a *mirrored* preview image. Confirmed
with a real test image comparing old vs. new landmark coordinates
against the same frame: old gave x=0.386 for one hand, new gives x=0.607
for the corresponding one -- `1 - 0.386 ≈ 0.614`, matching the expected
single-flip math. Fixed: detect on the raw frame, mirror the landmarks
once, mirror the frame separately for the preview. A regression test
(`test_detection_runs_on_the_raw_frame_not_the_mirrored_one`) asserts
the tracker's `detect()` is called with the frame `read_raw_frame()`
returned, not a mirrored copy -- the existing test suite's `mirror=lambda
f: f` identity fixture meant this exact bug was structurally invisible
to it before.

**Background blur, verified real before building.** Checked feasibility
first: MediaPipe's free, local, Apache-2.0 selfie segmenter (same
Google-hosted, no-key model family as hand tracking) -- 9ms steady-state
against a real image, well inside the preview's 250ms/4fps budget.
Confirmed category 0 = person / 255 = background empirically (corner
pixels vs. centre pixels of a real image), not assumed from a model
card. Applied to the *preview frame only* (landmark detection always
sees the real, unblurred pixels -- blurring shouldn't be able to degrade
tracking accuracy) and only when the owner turns it on: the segmenter is
built lazily on first enable, so leaving it off costs nothing. Toggled
from the dashboard (a `BLUR BG` button next to the existing theremin
toggle), not voice -- purely cosmetic, no capability question, rides the
same `CAMERA` green tier gesture tracking already has. New `ClientEvent`
`gesture.blur` goes straight from `core/ws.ts` to the `eyes` connection,
bypassing the skill layer entirely -- there's no "session" concept the
dashboard needs to reference, just "the one running gesture loop, if
any," which `eyes` already tracks.

A real bug surfaced immediately when the blurrer was run against a real
image, not caught by any test (all fakes return opaque markers, never a
real array with a real shape): `category_mask.numpy_view()` returns
`(H, W, 1)`, and appending another broadcast axis gave `(H, W, 1, 1)`
against the frame's `(H, W, 3)` -- reshaped explicitly instead of
assuming a shape.

**Consequences.**
- 82 Python tests (was 74), 488 TS, `make check` green.
- Verified against a real image (segmentation correctness, arm/finger
  edges) and a real 3-second camera run with blur on: landmark rate held
  at 10.8fps against the 12fps target (11.5fps without blur) -- close
  enough that blur doesn't meaningfully cost the tracking budget.
- The owner's third ask in the same report -- hand tracking driving the
  *real* OS cursor, with a voice-triggered click -- is a capability-tier
  decision (CLAUDE.md § 5), not a bug fix or a cosmetic toggle, and is
  being raised with the owner directly rather than built silently.
