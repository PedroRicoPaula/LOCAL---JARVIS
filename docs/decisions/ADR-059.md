## ADR-059 — The "peanuts" bug fixed: don't trust the degraded model's disambiguation choice

**Status:** accepted

**Context.** ADR-038 root-caused this precisely but shipped no fix: a
degraded-mode benchmark (`bench/bench_disambiguation_fallback.ts`,
forcing disambiguation onto the true last-resort provider) measured
42.9% (3/7) -- every fact/preference statement about the owner ("I
don't eat peanuts, I'm allergic") misrouted to a `shopping_list` intent,
`disambiguated: true` in every failure, meaning the model *actively
chose wrong*, not a shortlist or embedding problem. Against the healthy
primary model, disambiguation already said "none" correctly every time
-- this only ever happens when NIM is unreachable and disambiguation
falls back to `qwen2.5:0.5b`. Two prompt-wording fixes were tried and
benchmark-rejected in ADR-038 (one even regressed two unrelated,
previously-correct cases) -- confirming the problem was never the
prompt's wording.

**Decision.** Stop trusting this specific provider's disambiguation
judgment at all, the same call `core/router/laneClassifier.ts` already
makes for the identical reason (ADR-040: "a model that answers fast but
wrong is worse here than defaulting to unsure"). `disambiguate()`
(`core/skills/dispatch.ts`) now captures which provider actually
answered via `routeChat`'s own trace callback; when it's `"ollama"` (the
true last resort), the call returns `null` -- the exact same safe
default already used when the model's JSON is unparseable or names a
candidate outside the shortlist. No prompt touched, so none of ADR-038's
regression risk applies. Not a new behavior, just a new condition that
reaches an already-existing one.

**Verified against the real benchmark built for this exact purpose, not
a new one guessed at:** `bench_disambiguation_fallback.ts` -- **100%
(7/7), up from the 42.9% baseline** -- every fact-statement case now
resolves to "none," and the two legitimate `shopping_list` commands in
the same suite still dispatch correctly (the fix doesn't over-correct).
New unit test in `core/skills/tests/dispatch.test.ts` covering the same
property with a fake `"ollama"`-id provider, for regression coverage
that doesn't need real models or real network.

**A second, unrelated real bug found by then re-running the healthy-
model benchmark** (`bench_skill_routing.ts`, run as a matter of course
per ADR-038's own "check both benchmarks" discipline): "abre o Cursor se
faz favor" (open the Cursor app) started misrouting to the newly-added
`look.start_pointer_control` intent (ADR-056/058, same day) --
`start_pointer_control`'s own PT-PT examples used the bare word
"cursor," colliding with `launcher.open_app`'s existing "Cursor" (the
code editor) example. The exact same "a word becomes a magnet" failure
`skills/shopping_list/manifest.ts`'s own docstring already documents
avoiding for "coffee," and `launcher/manifest.ts`'s own comment already
documents once before for this identical app name -- just newly
reintroduced by this session's own pointer-control work. Fixed by
rewording every pointer-control example to "mouse"/"rato" instead of
"cursor" (same meaning, zero collision risk) -- `description` fields
were left untouched, confirmed they're never embedded for routing
(`core/skills/embeddingMatch.ts` only indexes `examples`).

**Consequences.**
- `bench_skill_routing.ts`: 88.6% -> 94.3% (recorded baseline updated,
  `bench/update_baseline.ts`) -- the Cursor collision fix alone accounts
  for the jump; the two remaining failures ("run the test suite," "we're
  almost out of rice") are pre-existing and unrelated, not touched here.
- `bench_disambiguation_fallback.ts`: 42.9% -> 100%.
- 108 Python tests, 498 TS (was 497), `make check` green.
- `docs/BACKLOG.md`'s "peanuts" entry closed out.
