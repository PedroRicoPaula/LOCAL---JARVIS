## ADR-066 — Two dashboard defects: a silently-swallowed write, and a signal built but never rendered

**Status:** accepted

**Context.** Both found by the same read-only analysis pass as ADR-065.

---

**1. Dashboard writes claimed success and swallowed the failure.**
`toggleTask`, `deleteTask` and `deleteShoppingItem` each mutated local
state optimistically and then called `fetch(...).catch(() => undefined)`
with **no `res.ok` check**. A 4xx/5xx doesn't reject a `fetch`, so the
`.catch` never even ran: the item disappeared from the dashboard while
still sitting in the database.

This is precisely the failure `core/persona.md` gained an explicit rule
against after a real live incident during SOAK (JARVIS said it had
deleted a shopping-list item that was never touched). The rule applies
to the dashboard for the same reason it applies to the voice -- the UI
claiming a change happened when it didn't is the same lie in a different
channel. The read path (`fetchJson`) has checked `res.ok` since it was
written; only the write path skipped it.

Fixed with a shared `optimisticWrite(path, method, rollback)`: it
verifies `res.ok`, puts the previous state back on failure, and surfaces
the failure into the dashboard's own Error Log panel rather than
reverting silently.

---

**2. `sense.connection` was broadcast, declared, and dropped.**
`core/main.ts` has broadcast it since ADR-051's reconnect work,
`ui/src/lib/types.ts` declared it, and `use-jarvis.ts`'s event switch had
no `case` for it -- it fell through to `default: break`. The type's own
docstring says the entire point was that "a dropped sense connection had
no dashboard-visible signal at all." It still didn't.

Fixed: the event is handled into a `SenseConnections` state and rendered
as three labelled dots in the status bar next to the existing CORE
indicator.

**A second, real gap surfaced while verifying it live**, which is why
this needed more than a `case` statement: `sense.connection` only fires
on a *change*, so a freshly-opened dashboard showed all three senses as
"no report yet" indefinitely even with all three connected -- verified in
a real browser, where the dots rendered grey against a fully-connected
`core`. `createWsHub` now takes an optional `backfillForNewClient`, and
`core/main.ts` keeps the current state and seeds it at startup, so any
tab opened at any moment is told the truth. Same reasoning as
`/api/approvals`' existing backfill (SPEC.md § 8's "close the browser
mid-approval, request survives") applied to live status.

A sense nothing has been heard about yet renders dim, not red: "not
reported yet" and "down" are different states, and showing the second
when it's the first is exactly the confidently-wrong signal CLAUDE.md
§ 6 warns about.

**Consequences.**
- `make check` green (547 TS + 108 Python), `next lint`/`tsc` clean.
- Verified in a real browser against a running `core`: the dots render
  cyan for all three connected senses, and were confirmed grey before
  the backfill was added -- the fix was driven by the real observed
  behaviour, not by reading the code.
