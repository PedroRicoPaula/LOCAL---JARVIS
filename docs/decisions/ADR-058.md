## ADR-058 — Pointer control: 8 real findings from a dedicated security review, all fixed

**Status:** accepted

**Context.** With the repo now public and `POINTER_CONTROL` being the
first capability that drives the real OS from hand tracking, a
dedicated `security-auditor` review (2026-08-13) was run specifically
against `senses/eyes/pointer.py`, its integration into `gestures.py`/
`main.py`, and the capability's wiring through `core/`. Full agent
report kept in this session's own record; summarized here per finding.

**1. HIGH — the click-safety key was overloaded, so an unrelated
keypress could fire an unintended click.** The default trigger was
Space -- the single most overloaded key on a keyboard (types a
character, pauses media, activates a focused button in most UI
toolkits), and the listener never suppressed it. Any Space press for a
completely unrelated reason, while pointer control happened to be on
and a hand happened to be visible, fired a real extra click wherever
the hand last mapped to on screen -- reproducing exactly the harm
ADR-056's design exists to prevent: a physical key proves *a* keypress
happened, not that the owner *intended a click there*. Two independent
fixes:
- Default trigger changed to `ctrl_r` (right Control alone) --
  verified live to resolve to a real, distinct pynput keycode (62,
  vs. 59 for generic ctrl) -- typed alone it produces no character and
  has no bound meaning in virtually any macOS app, unlike Space.
- A click's edge no longer counts unless the hand is *also* in a
  deliberate pointing pose (`is_pointing`: index extended, other three
  fingers curled -- mirrors `ui/src/lib/hand.ts`'s existing
  `extendedFingerCount` logic, now with a Python equivalent) at that
  same instant. Verified against real MediaPipe output (not just
  synthetic test fixtures) that the function runs cleanly on real
  21-point landmark data.

**2. MEDIUM — `POINTER_CONTROL` was documented but never enforced.**
`ctx.camera` was gated on `CAMERA` at handout (`core/main.ts`), but
once a skill had that handle, `startPointerControl`/
`stopPointerControl` were reachable regardless of whether the manifest
also declared `POINTER_CONTROL` -- contradicting CLAUDE.md § 5's "every
skill declares the capabilities it needs, the gate enforces them." Not
exploitable today (`look` is the only `CAMERA` skill and legitimately
declares both), but nothing would have caught a second skill getting
free cursor access. Fixed: `restrictPointerControl()` (`core/skills/
camera.ts`) wraps the handle so those two methods throw unless the
manifest also has `POINTER_CONTROL`, wired into the exact spot
`core/main.ts` already gates `CAMERA`. 5 new unit tests
(`core/skills/tests/camera.test.ts`).

**3. MEDIUM — no durable record that a click fired.** Every other
green-tier action in this codebase has the same underlying gap
(CLAUDE.md's "Green: ... Logged" isn't fully built for any of them
yet) -- but pointer control is the first with a real, potentially-
irreversible external side effect, so it's the one that needed fixing
now rather than waiting for a broader logging pass across the whole
green tier (that stays a separate, explicitly-not-done item, not
silently expanded into this fix). `gestures.py` now emits a
`pointer.click` event on every real click; `core/main.ts` records it
via `memory.appendEvent({kind: "action", ...})` -- a real `events` row,
not just the ephemeral WS status broadcast.

**Correction, 2026-08-13:** "every other green-tier action has the same
gap" was wrong -- checked before extending this pattern to
`APP_CONTROL`/`REMINDERS`, not assumed. `Gate.propose()`
(`core/gate/gate.ts`) already calls `logAudit()` for *every* green-tier
action that goes through `ctx.propose()`, `approval_id: null` standing
in for "no approval row needed" -- confirmed against real rows in
`data/jarvis.db`'s own `audit_log` table (`green_auto_run`/`executed`/
`execution_failed` entries for real `APP_CONTROL` calls from this same
session's own earlier testing). `skills/tasks/index.ts` routes through
the identical `ctx.propose()` path, so `REMINDERS` has the same
guarantee. The real, narrower reason pointer control needed its own
fix: it's the one green-tier action that bypasses `ctx.propose()`/the
Gate entirely (a deliberate design choice -- continuous WS-relayed
state, not a per-utterance skill dispatch), so nothing else was ever
going to log it. No other green capability has that same structural
gap; this was not a pattern to extend further.

**4. MEDIUM — the `eyes` Unix socket had no permission hardening.**
`senses/ipc.py`'s `listen()` didn't `chmod` the socket, so any other
local process running as the same user could in principle connect and
send `arm`/`gesture.start`/`pointer.control` as if it were `core`.
Bounded in practice (an attacker with local code execution as this
user could already drive `pynput` directly, bypassing this socket
entirely) but real, and cheaper to close than to leave. Fixed:
`os.chmod(socket_path, 0o600)` right after bind.

**5-8, LOW, all fixed:** `_click_was_pressed` now explicitly reset when
a click trigger is (re)created, rather than relying on a fresh
`PynputClickTrigger` happening to never report a stale press.
`bool(message.get("enabled", False))` replaced with
`message.get("enabled") is True` in `senses/eyes/main.py` --
`bool("false")` is `True` in Python, a real trap for anything poking
the socket by hand (not reachable via the real TypeScript caller,
which always sends a JSON boolean, but not something a message handler
this close to a raw socket should depend on). `map_to_screen` gained an
`isfinite` guard (not reachable today -- landmarks are never wire-
deserialized -- but cheap). `senses/ipc.py`'s `read_lines()` gained a
10MB cap so a peer that never sends `\n` can't grow the buffer
unbounded.

**Consequences.**
- All 8 findings fixed, none deferred silently.
- 108 Python tests (was 103), 497 TS (was 492). New regression tests:
  `is_pointing` unit tests (pointing/open-palm/fist/missing-landmarks),
  a test proving a real key edge with a non-pointing hand does *not*
  fire a click, `restrictPointerControl`'s full behavior (allows
  gestures, blocks pointer methods, reads `state` live not cached).
- Two existing tests (`test_click_fires_once...`,
  `test_pressing_and_releasing_twice...`) needed a real pointing-pose
  fixture instead of the old one, which happened to satisfy the
  pre-fix code by coincidence, not by modeling a real pointing hand --
  a good example of exactly the gap `is_pointing` closes.
- `make check` green throughout.
- **Owner-required, unchanged from ADR-056:** whether `ctrl_r` and the
  pointing-pose requirement feel right in real use is still the
  owner's own hand, own key, own judgment to make.
