## ADR-064 — The `converse` lane was fully synchronous; CLAUDE.md § 7's budget finally measured

**Status:** accepted

**Context.** CLAUDE.md § 7 has said since v0.1:

> The `converse` lane has a hard budget: first audible syllable within
> 1.5s of the owner finishing speaking. [...] Never `await` a full model
> response before starting playback. If you build it synchronously "for
> now", it will never be fixed. Do not.

Checked 2026-08-17: **nothing had ever measured it**, and the rule was
being violated by the most-used path in the system.
`generalConversationReply` called `router.complete(...)`, which streams
internally but accumulates every token into a string before returning;
`core/main.ts` then called `conversation.say(fullText)` once. So JARVIS
sat silent for the entire generation on every utterance no skill claimed
-- which is the fallback for everything.

**Measured first, then fixed.** New `bench/bench_latency.ts` runs 5 real
utterances (EN + PT-PT) through the real `converse` provider chain and
reports both halves separately:

| | p50 | p95 |
|---|---|---|
| first non-empty chunk (when TTS *could* start) | **424ms** | 615ms |
| full response (when it actually started) | **2343ms** | — |

So the synchronous shape cost **~1.9s of avoidable silence per turn**,
and overshot § 7's own 1500ms budget by roughly 800ms, while the
streaming path clears it nearly 4x over. That gap is the entire finding;
neither number alone shows it, which is why the benchmark reports both.

**Decision.** `generalConversationReply` now streams, taking an optional
`onSentence` callback and emitting each sentence the moment it completes;
`core/main.ts` passes `conversation.say`. New `core/sentenceStream.ts`
(`SentenceAccumulator`) does the incremental splitting -- the TypeScript
counterpart to `senses/voice/sentences.py`, which does the same split one
stage later. Splitting *there* alone never helped: `voice` only receives
a reply after `core` has finished awaiting every token of it.

Verified against `senses/voice/main.py`'s own `run_forever` before
relying on it: it reads `speak` messages sequentially and `SayBackend.
speak` blocks until each one's audio finishes, so sentence-by-sentence
delivery plays back in order with no overlap. Confirmed live end to end
-- a real PT-PT technical question produced **6 separate `speak`
messages** on the socket where it previously produced one.

`onSentence` is optional, so any caller wanting only the final text keeps
the previous shape exactly.

**Consequences.**
- 532 TS tests (was 520) + 108 Python, `make check` green.
- New tests cover the failure modes that matter for speech: every
  sentence spoken exactly once, the reassembled sentences equalling the
  returned text, a single unterminated sentence still spoken, a reply
  with no punctuation at all still spoken, and the empty-reply fallback
  still spoken rather than leaving the owner in silence.
- `bench/bench_latency.ts` is a permanent guard on a rule that had none.
  Baseline recorded at 80% within budget -- deliberately loose, since
  this measures real network and real provider variance.
- **Not fixed here:** a skill's own `ctx.say()` is still called once with
  a complete string. Skills compose short, templated replies rather than
  streaming long generations, so the same ~2s gap does not apply; if a
  future skill streams a long answer, it should take this same shape.
- Noted while verifying live: European Portuguese still drifts toward
  Brazilian forms on *long* technical answers ("elas se carregam" rather
  than "carregam-se") even with ADR-062's persona rules in place. The
  rules hold on short replies; long generations wander. Logged, not
  chased further here.
