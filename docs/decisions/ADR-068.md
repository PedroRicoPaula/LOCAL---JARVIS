## ADR-068 — Proving the gate's security invariants, and one real gap found doing it

**Status:** accepted

**Context.** The gate is this project's only security boundary
(CLAUDE.md § 5: model output never reaches an executor; the gate turns
proposals into actions). Its 29 existing tests covered the state
machine's happy and sad paths thoroughly -- but not whether the boundary
holds against a caller actively trying to break it. Several load-bearing
invariants were true only *accidentally*, with nothing to catch a future
refactor that broke them.

**Invariants now proved by real adversarial tests, all of which passed
on the existing code:**

- **An approved action executes exactly once, even under a genuine
  race.** Two `decide()` calls fired concurrently on the same request
  (the real double-click shape) with an executor that yields mid-run.
  This holds because every check from `getApprovalRow` through
  `setState(id, "approved")` is *synchronous*, so Node's single thread
  cannot interleave a second `decide()` into the middle of it -- true,
  but nowhere written down and trivially broken by making any of those
  steps async later. The loser is logged as a `replay`, not silently
  dropped.
- **Approve and reject racing settle exactly one way**, and the action
  still runs at most once.
- **A tampered signature fails**, field by field: payload swapped, id
  swapped, nonce swapped, one character of the signature edited, and a
  different key. Each mutated independently, so no single check can be
  passing for the wrong reason.
- **A signature cannot be pasted between requests** -- this is what
  binds a signature to one specific approval rather than to a payload
  shape.
- **A settled request cannot be revived**: approving something already
  rejected leaves the state untouched and logs exactly one replay.
- **A decision for an id that never existed** is a logged replay, not a
  crash.
- `timingSafeEqualStrings` is correct on prefixes, empty strings, and
  non-ASCII (`"ção"`) -- it compares char codes, so a multi-byte
  character was worth proving rather than assuming.

**The real gap found: `issuedAt` was not covered by the signature.**
A signed execution's timestamp could be changed freely and still verify.
Harmless in-process -- freshness is enforced by the gate's own
`expires_at` check against the DB row, never by the signature -- but this
signature exists *specifically* so a future out-of-process executor can
trust what it receives (SPEC.md § 8's webhook case, ROADMAP Phase 13),
and such an executor has no DB row to check against. An unsigned
timestamp would have handed it a replay window. Now signed;
`canonicalPayload` covers `{id, nonce, payload, issuedAt}`. No migration
concern -- signatures are generated in `decide()` and consumed
immediately, never stored.

**Also documented rather than changed:** the payload's own internal key
order still comes from however it was built or parsed. That is fine
today (sign and verify see the same object, and a JSON round-trip
preserves order), but a future executor that re-serializes a payload
through anything that reorders keys would break verification. Written
into `canonicalPayload`'s comment so it is found before someone builds
against it, not after.

**Consequences.**
- 561 TS tests (was 553) + 108 Python, `make check` green.
- Worth noting how the `issuedAt` gap surfaced: not by reading the code
  looking for bugs, but by writing a test that asserted what I *assumed*
  was true and watching it fail. The first version of that test asserted
  `issuedAt` was unsigned and passed; it is now inverted.
- `tsc` also caught a real mistake in the new tests that `node --test`
  did not -- the tests ran green while using a wrong `ApprovalResponse`
  shape, because types are stripped at runtime. A reminder that
  `make check` running both is doing real work.
